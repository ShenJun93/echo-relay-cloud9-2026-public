*Cloud9 × JetBrains 2026, Category 3. Prepared public-facing case study, not a Devpost submission.*

## The challenge: build a game a fan can learn in seconds

At a live event, visitors need a playable, self-contained experience rather than a long tutorial. I built ECHO//RELAY, a 60-second browser arcade with one action: switch between two lanes. Each switch leaves a temporary Echo that can collect a signal on the lane the player just left. Catch both signals in a wave to form a Dual Link.

The game uses an original TypeScript simulation, Vite, canvas rendering, keyboard/touch controls, synthesized sound and a Service Worker. It does not require a user account, paid API or online leaderboard. The apparent goal is simple; deciding *when* to switch is the skill.

## The useful failure: a passing game with a poor incentive

Early tests verified that the game finished a 60-second run, recorded scores and survived offline reload. A conventional “spam input” bot pressed Space every 15 frames and seemed unremarkable.

The stronger audit tested many *cooldown-aligned* repeated-switching policies on the actual engine with a fixed seed. A blind policy switching every 37 frames at a favorable starting phase scored **42,260 points** and **32 Dual Links**, despite observing no packet position. An idle player scored **4,030**. The previous Echo duration (0.54s) nearly covered the previous lane until the next permitted switch (cooldown 0.60s), so a player could automate coverage of both lanes.

This was a gameplay-design problem, not a security vulnerability or a scoring injection. Simply having 15 passing tests had not proven a meaningful skill curve.

## From reasoning to a tested fix

A parameter sweep suggested a narrower Echo and longer cooldown. The candidate reduced Echo persistence from **0.54s → 0.33s** and increased the minimum switch interval from **0.60s → 0.80s**. It also synchronized the visual fade timing, updated player-facing wording, and split local scoreboard storage so earlier rules did not compete with later ones.

The test suite gained an adversarial regression that scans multiple repeated-input periods and every initial phase on the event seed. The updated candidate reached **16/16 tests PASS**, TypeScript/Vite build PASS and the full local browser QA suite PASS. In the sampled P35 parameter sweep, the best blind-periodic score dropped from **41,060** on the old parameters to **18,060** on the candidate. This is a deterministic machine-policy comparison, **not human fun testing or a claimed statistical effect**.

That experience shaped the build process: do not treat automated tests as evidence of every product goal. Add a test for the *behavior or failure incentive you care about*, not just the mechanics that are easy to automate.

## An offline label is not a reload guarantee

A later audit found that the live P72 build reported the same offline label when the service worker was blocked, the shell was cached, or its cache was evicted. Only the cached case could reload offline; all three already-loaded tabs could start a round. The source-pinned candidate (4adc012) distinguishes current-tab play from cached reload readiness, checks the shell and required JavaScript/CSS responses, and updates the status after simulated late eviction. It avoids repeated accessibility announcements when the verified state is unchanged. This work was implemented and tested with outside-IDE automation.

Six isolated browser regression scenarios passed, including missing JavaScript, incorrect CSS MIME, and late eviction; the label layout passed 14 state/viewport checks. These are local candidate results, not public deployment evidence or a permanent offline-storage guarantee.

## Native WebStorm code inspection

On 24 November 2026, the WebStorm 2026.3 command-line inspector completed on the candidate source with exit code 0 and XML results. The default-profile run reported 164 CSS unused-symbol warnings (58 distinct selector names, all found as literals in the dynamic UI source), two redundant-local-variable warnings in the renderer, and one grammar suggestion in a comment. No functional change was justified by those findings. In particular, blindly deleting the reported CSS would risk removing styles used by dynamically generated markup. The report generator also logged missing descriptions for some unrelated inspection tools; this is not a claim that every possible inspection ran or that the code is defect-free.

This is a genuine additional JetBrains analysis step, separate from the earlier native refactor and the shell-based implementation. No Junie or Air usage is claimed.
